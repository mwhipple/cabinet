#+title: al/container-sandbox
* Background
What seems to be one of the most useful tools to provide out of the
gate is a standard POSIX-y shell environment. This would allow the
agent to perform a variety of work without further logic. A naive
approach would also pose signficiant security concerns given that it
would allow wide access to the underlying system. Existing mecahnisms
should be used to provide a more controlled sandbox, where one of the
most supported such mechanisms is the use of containers. This tool
should therefore be designed such that the tool is defined to define a
containerized environment, and those calls requested by the agent will
be run within that environment.
** Portability
The containerization should be prefer using portable approaches rather
than making use of anything that introduces unnecessary abstractions
or constraints. For example: generating a system call that would
compose a docker CLI compatible command would be appropriate (with
appropriate guards against any kind of injection attacks). Any
configurations should be modeled as reasonably self-documenting
objects - while the actual implementation used may be portable and
low-level, the provided interface should provide expressive logical
constructs rather than leaking out implementation details.
** Features
The options available for the sandbox creation is based on
standard concepts. The starting set should include those that allow
for interacting with local files while providing maximum protection
that anything other than such file protections would be prevented.
** Interaction Model
The general expected model is one where the produced sandbox should be
able to be treated like a resource, and while it is open commands can
be sent to it.
** Division of Responsibilities
Some responsibilities will be distributed between this logic and the
container. There will therefore be an expectation that the images used
provide some expected behaviors. This will largely be driven by
pragmatism and what seems to provide the clearest end solution.
** Escaping
One of the stickier details to work through across various
implementations will be escaping details. Right now this is mostly
just identifying this as a problem to track (with mitigations
hopefully to follow). Issues with escaping should manifest as error
results, but can then lead to churn and inefficient tool use. This can
be addressed through some combination of additional logic and guidance
provided to the agents as part of the tool declaration.

from dataclasses import dataclass
from typing import Any
import abc

@dataclass(frozen=True)
class ContainerArgument(abc.ABC):
    """Abstract base class for container launch arguments.

    This is a sandbox-independent representation of container arguments.
    Each sandbox implementation provides its own method to render these
    arguments in the format required by that sandbox's container runtime.
    """


@dataclass(frozen=True)
class BindMount(ContainerArgument):
    """Bind mount a host directory into the container."""
    source: str
    target: str


@dataclass(frozen=True)
class TmpFSMount(ContainerArgument):
    """Mount a tmpfs filesystem inside the container."""
    target: str
    size_mb: int = 0


@dataclass(frozen=True)
class EnvironmentVariable(ContainerArgument):
    """Set an environment variable inside the container."""
    name: str
    value: Any
